ScopeGuard — Final Adversarial Audit
====================================

Audit date: October 6, 2026
Repository: Pr1meGG/paypal-ai-hackathon

RECOMMENDATION
--------------

PIVOT.

Preserve the useful contract-to-payment concept, but reposition it around a
narrow, evidence-backed amendment workflow. The current “mission-critical
enterprise governance” proposition exceeds both the implementation and the
demonstrated differentiation.

Evidence labels:
  [A] VERIFIED — directly supported by inspected source, executed offline
      probes, or retrieved primary sources.
  [B] REASONABLE INFERENCE — judgment grounded in that evidence.
  [C] UNVERIFIED / SPECULATIVE — requires additional evidence.

Verification boundary:
  Backend probes executed pinned source in memory with isolated SQLite,
  injected configuration, and blocked or mocked provider calls. Static
  hosting was omitted from that harness. Actual OpenAI responses, PayPal
  sandbox transactions, browser interaction, and a clean-checkout
  installation are UNKNOWN — NOT VERIFIED. This was a read-only audit.


1. EXECUTIVE VERDICT
--------------------

ScopeGuard contains a real, compact backend prototype and substantial
frontend styling. Its most important guarantees currently fail:

1. [A] Payment failures become successful financial records. Missing
   credentials, unknown orders, and rejected capture attempts can produce
   COMPLETED responses and persisted PAID classifications.

2. [A] The shipped frontend has two independent integration failures. HTML
   loads module-exporting JavaScript as a classic script; all 47 unique
   literal DOM IDs targeted by that JavaScript are absent from the HTML.

3. [A] AI output crosses into financial authority. A controlled
   model-output probe containing classification="PAID" was accepted and
   persisted without a PayPal order or capture.

4. [A] Default analysis does not reliably respect the contract. Explicitly
   included QuickBooks work was classified as extra. The supplied
   database-migration scenario was classified as included despite explicit
   exclusion.

5. [A] The proposed category already has direct competitors. EasyScope,
   ChangeVerdict, and Boundr publicly advertise closely overlapping
   workflows.

[B] These findings support a strategic pivot, rather than further investment
in dashboard breadth. Repairing the implementation alone would still leave
weak differentiation. The surviving opportunity is to make agreed changes,
commercial approval, and payment evidence reliably correspond for one
specific customer segment.

3. ARCHITECTURE REALITY
------------------------

ACTUAL ARCHITECTURE

  Manual SOW/request input
          |
          v
  FastAPI scope router
          |
          v
  One OpenAI JSON request, or keyword fallback
          |
          v
  Project + mutable ScopeChange rows
          |
          v
  Price-setting/order endpoint
          |
          v
  PayPal OAuth + Orders v2 helper
          |
          v
  Capture endpoint
          |
          v
  Local classification, history projection, KPI sums

[A] This is a synchronous, single-merchant application. Payments use one
globally configured PayPal account. There is no implemented autonomous agent
loop, multi-merchant onboarding, document-processing pipeline, or separate
transaction ledger.

EXECUTION TRACES

Workbench submission:
  POST /api/scope/analyze creates a new Project every time, commits it, then
  calls analyze_scope. It does not match an existing baseline despite the
  “provision or match” comment.

Analysis persistence:
  Model/fallback output is converted to the broad ScopeStatus enum and
  stored. That enum includes financial states such as PAID.

Commercial approval:
  Direct order creation accepts caller-supplied price and currency, optionally
  updates a scope row, and sets MERCHANT_APPROVED. No authenticated merchant
  identity is established.

Order creation:
  The helper obtains an OAuth token and posts a CAPTURE-intent order. The
  router catches exceptions and manufactures an order ID and sandbox-looking
  checkout URL.

Buyer return:
  /api/paypal/return?token=... renders a success page. It does not verify the
  token, fetch order state, or record buyer approval.

Capture:
  The helper posts to PayPal and extracts the first capture ID. Routers ignore
  payment verification requirements and can mark the row paid after
  exceptions.

History:
  Returns up to 100 scope rows. Channel is always “Slack”; an order ID alone
  is projected as “AUTHORIZED”.

Browser ledger:
  Initializes fabricated sample rows. The defined history-fetch method is not
  used to hydrate it.

Browser capture attribution:
  updateLedgerStatus(_orderId, ...) ignores the order ID and updates the
  newest ledger entry.

Webhook inspector:
  Constructs random browser payloads and displays “Delivered ... 200 OK”. No
  network dispatch or backend receiver exists.

Contract vault:
  Loads hardcoded examples. No signed-document verification, upload
  processing, versioning, or amendment incorporation exists.

STRUCTURAL CONSEQUENCES

- [A] Scope classification and payment lifecycle share one mutable field.
- [A] Raw PayPal evidence, actual payer information, actual fees, approval
  actors, and request-attempt history are not durably represented.
- [A] Direct analyses fragment the same customer/project into separate
  records.
- [A] Paid amendments do not update the contract baseline.
- [B] Consequently, this architecture cannot substantiate its “immutable
  compliance ledger” or ongoing contract-governance claims.

SQLite and vanilla frontend technology are reasonable choices for a
hackathon. The blocking issue is the integrity of the connections between
them.

AI QUESTIONS ANSWERED

1. What model integration exists?
   [A] OpenAI Chat Completions, default model gpt-4o-mini.

2. Is Anthropic implemented?
   [A] No. Other provider settings fall through to the heuristic.

3. Is analysis multi-stage?
   [A] One prompt and one JSON response.

4. Is there retrieval or clause indexing?
   [A] No. Full supplied text is placed in the request.

5. Does fallback compare contractual meaning?
   [A] Classification depends on request keywords; contract text supplies
       superficial quote fragments.

6. Are evidence quotes validated?
   [A] No substring/span validation or clause-reference verification.

7. Can it abstain?
   [A] No supported uncertainty outcome. Controlled UNCERTAIN output caused
       HTTP 500.

8. Are mixed requests independently classified?
   [A] One overall verdict; itemized strings have no per-item evidence or
       classification schema.

9. Where does pricing come from?
   [A] Model-invented “fair market” prices, or $250 per matched keyword.

10. Is confidence calibrated?
    [A] HIGH maps to 0.95, MEDIUM to 0.80, otherwise 0.60; no calibration
        evidence.

11. Is financial output constrained?
    [A] No. classification is a plain string subsequently accepted against
        an enum containing financial states.

12. What happens on model failure?
    [A] Silent semantic degradation to the heuristic; output retains
        apparent high confidence.

13. Is prompt-injection resistance demonstrated?
    [C] UNKNOWN — NOT VERIFIED. Controlled output probes establish
        inadequate validation, not successful exploitation of a live model.

14. Is AI quality evaluated?
    [A] Existing tests cover three friendly examples, with no counterfactual
        grounding, ambiguity, citation, or adversarial assertions.

15. Is AI necessary?
    [B] Potentially useful for interpreting unstructured, mixed requests.
        The current default demo can run without a model, so meaningful AI
        benefit remains unproved.

VERIFIED FAILURES

Counterfactual grounding test:

  Request: “Please add QuickBooks sync.”

  Contract: “QuickBooks sync is included.”
    Result: EXTRA_PROPOSED, $750

  Contract: “QuickBooks sync is excluded.”
    Result: EXTRA_PROPOSED, $750

[A] Reversing the contractual boundary did not reverse the verdict.

Supplied preset tests:

  Database migration:
    Contractual boundary: Legacy migration explicitly excluded.
    Result: INCLUDED, $0, HIGH.

  SSO/RBAC:
    Contractual boundary: Separate authorization of $3,500 specified.
    Result: EXTRA_PROPOSED, $1,750, HIGH.

  Minor fix:
    Contractual boundary: Warranty fixes included.
    Result: INCLUDED, $0, HIGH.

[B] AI should assist with evidence and proposed amendments. The server must

6. FINANCIAL SAFETY
-------------------

ASSESSMENT: FAILED.

These are reproduced application-integrity failures. The probes did not move
money or demonstrate a vulnerability in PayPal.

Invariant: Failed order creation must remain failed.
Result: Missing credentials produced a manufactured ORDER-PP-... ID and HTTP
        200 CREATED response.

Invariant: Failed capture must not become paid.
Result: Missing credentials produced HTTP 200 COMPLETED and persisted PAID.

Invariant: Capture requires an appropriate order and approved commercial
           state.
Result: Legacy capture changed an INCLUDED, $0 record with no order into PAID.

Invariant: Unknown orders must not produce receipts.
Result: Unknown order returned a fabricated $500 completed receipt.

Invariant: Pending funds must remain pending.
Result: Mocked €1 pending capture was reported as a completed $750 USD
        payment.

Invariant: Capture amount, currency, and reference must match approved terms.
Result: Wrong amount, currency, and reference were ignored.

Invariant: Missing capture evidence must not create a contradictory state.
Result: Documented minimal response caused HTTP 500 after committing PAID with
        no capture ID.

Invariant: Paid records must not silently change commercial terms.
Result: Recreating an order changed $750 to $990, replaced the order, and
        retained the old capture ID.

Invariant: Amount/currency input must be valid.
Result: $0.001 and ZZZZ were accepted; persisted amount became zero cents.

Invariant: Financial state must be independent of model verdict.
Result: Controlled PAID model output directly entered the database.

IDEMPOTENCY AND RETRIES

[A] Repeated create and capture helper calls generated different
PayPal-Request-Id values.

[B] The application lacks retry-safe operation identity, durable attempt
tracking, and recovery for “provider succeeded but application timed out.”
PayPal may still reject duplicate capture of an already captured order; this
audit does not establish that the same order was double-charged.

FINANCIAL TRUTH IS ALSO DISTORTED DOWNSTREAM

- History calls an order AUTHORIZED merely because an order ID exists.
- Fees and payer email can be invented rather than extracted.
- KPIs sum mutable commercial amounts rather than verified capture amounts.
- Currency-specific totals are not separated.
- Frontend capture attribution updates the newest ledger entry, regardless of
  order identity.

AUTHORITY AND ACCESS

[A] The audited routes have no authentication or ownership checks. Project
listing exposes stored briefs; payment-changing routes are callable without a
merchant identity.

[B] A deployed instance therefore lacks the authority boundary required by
its human-approval promise. PayPal’s buyer checks remain separate and cannot
substitute for application authorization.

13. FALSE CONFIDENCE
--------------------

The repository contains mechanisms that make incomplete behavior look
stronger than it is:

- “100% pass rates.” Payment tests pass without credentials because exceptions
  are converted into success.
- Sandbox-looking URLs. A URL containing paypal.com is sufficient for a test
  assertion even when its order ID was manufactured.
- “Objective confidence.” Numeric confidence is a fixed mapping, not a
  measured probability.
- “Verbatim citation.” Strings are accepted without source-span validation.
- “Immutable ledger.” Commercial terms and payment identifiers are overwritten.
- “Webhook delivered: 200 OK.” The browser prints this without sending a
  request.
- “Healthy.” /health reports process health and configuration presence,
  without provider authentication.
- “Protected revenue.” Proposed prices are summed as though loss had been
  prevented.
- Enterprise visual language. It implies controls, provenance and operating
  maturity the code does not establish.
- Historical [PROVEN] log entries. They do not verify the current snapshot.

[A] Empty-database KPI response:

  total_creep_prevented: 4850.0
  total_settled_revenue: 2850.0
  capture_rate: 100
  total_audits: 14

The frontend separately seeds sample clients, captured amounts, and compliance
metrics.

[B] These outputs obscure the difference between a demonstration fixture, an
attempted operation, and a verified business result. Intent is not
established; the misleading effect is.

   and retrieval exist.

3. [A] Recognizable PayPal integration primitives. OAuth, create,

4. [A] Credentials are accessed server-side. Current templates contain

5. [A] Timeouts and HTTP error checks exist inside provider helpers. The

6. [A] Considerable frontend design work exists. Reusable styling can support
   a smaller coherent experience.

7. [B] The core narrative is comprehensible. A client requests additional
   work; the business agrees terms and obtains payment before proceeding.

8. [B] A meaningful AI role is available. Decomposing mixed requests, finding

The most valuable reusable insight is:

  Keep the requested change, the governing evidence, the agreed commercial
  terms, and the payment receipt tied to the same amendment.

Its value and differentiation still require demonstration.


15. FINAL DECISION
------------------

TEN PRODUCT-SURVIVAL TESTS

1. Can the problem be explained quickly?
   PASS — Additional work begins before price/scope agreement.

2. Is one initial customer clearly selected?
   FAIL — Broad freelancer-to-enterprise positioning.

3. Does changing the contract change the decision?
   FAIL — Verified counterfactual fallback failure.

4. Does removing AI materially weaken the demonstrated product?
   FAIL — Default path relies on keywords; model advantage unmeasured.

5. Is PayPal meaningfully exercised in demonstrated behavior?
   FAIL — Real sandbox payment unverified; synthetic success dominates tests.

6. Is there a demonstrated advantage over existing tools?
   FAIL — Direct advertised competitors; no comparative evidence.

7. Does the product fit the customer’s existing workflow?
   UNKNOWN — Manual-paste friction and approval/payment habits unvalidated.

8. Will users trust and pay for it?
   UNKNOWN — No verified interviews, usage or willingness-to-pay evidence.

9. Are financial outcomes truthful under failure/retry?
   FAIL — Multiple reproduced integrity failures.

10. Can the current build support a credible sub-three-minute demo?
    FAIL — Frontend blockers and missing external proof.

DECISION: PIVOT

[B] Continuing the broad enterprise-governance positioning would invest in an

PRESERVE

- FastAPI project skeleton and reusable route/schema organization.
- Basic project/request persistence.
- Server-side PayPal integration primitives.
- Selected design tokens and styling.
- The evidence -> agreed amendment -> verified receipt insight.

DISCARD OR REPLACE

- Synthetic success in financial routes.
- Keyword classification presented as semantic contract understanding.
- Invented pricing and uncalibrated confidence presented as authoritative.
- Mutable state presented as an immutable audit ledger.
- Broad enterprise/compliance/escrow claims.
- Simulated integrations presented as operational capability.
- Unrelated RTO, lead-follow-up and rental-product assumptions.

ONE RECOMMENDED PIVOT HYPOTHESIS

Evidence-backed amendment checkout for small fixed-fee studios.

Problem:
  A mixed client request contains included corrections and additional work;
  the parties need to agree the paid portion before execution.

AI role:
  Decompose the request, cite exact baseline evidence, identify uncertainty,
  and draft an amendment.

Commercial authority:
  Merchant confirms scope and price from agreed terms; client explicitly
  accepts the amendment.

PayPal role:
  Collect the agreed amount and reconcile a verified receipt to that exact
  amendment.

Demo moment:
  One request contains free and paid work; only the agreed addition reaches
  checkout, and an altered clause or failed capture prevents a false
  charge/success.

Differentiation target:
  Demonstrably reliable grounding, refusal behavior, baseline versioning and
  amendment-to-capture binding.

Complexity:
  Moderate; one narrow workflow, but core state, evidence and frontend
  connections require substantial repair.

Hackathon fit:
  Credible if meaningful model behavior and real buyer-approved sandbox
  settlement are shown.

Commercial status:
  [C] Hypothesis. Competitors already overlap; uniqueness and willingness to
  pay remain unverified.

This is a product hypothesis to validate before expanding implementation.


16. NEXT 7 MOVES
-----------------

1. Select one customer and one approval/payment scenario.
   Produce a one-page scope naming the buyer, user, contract type, payment
   timing, and supported currency. Validate it against actual recent change
   requests.

2. Validate the proposed advantage against direct alternatives.
   Use the same realistic mixed request with EasyScope, ChangeVerdict and a
   manual workflow. Record time, evidence quality and approval friction.

3. Establish a portable, functioning vertical slice.
   Align script mode, DOM IDs, handlers, presets and dependency commands.
   Acceptance: a fresh checkout reaches analysis, order creation and history
   through the actual browser.

4. Restore deterministic commercial and financial authority.
   Separate AI verdicts from payment state; require ownership and explicit
   approved terms; remove manufactured payment success.
   Acceptance: rejected or uncertain operations never create paid records.

5. Prove PayPal end to end and under failure.
   Show buyer approval, seller-side capture, matching amount/currency/
   reference, minimal-response handling and retry recovery. Preserve provider
   evidence for the exact amendment.

6. Demonstrate meaningful AI quality.
   Evaluate included/excluded counterfactuals, mixed requests, amendment
   history, fabricated quotations and ambiguity. Report measured performance
   and model failures transparently.

7. Replace the submission narrative with verified reality.
   Consolidate documentation, provide complete judge access, and record a
   functioning demo under three minutes. Base impact claims on observed
   customer evidence or explicit hypotheses.

BOTTOM LINE
-----------

ScopeGuard has reusable foundations. Its next investment should prove a
narrow, trustworthy amendment-to-payment workflow and a customer advantage
before expanding the platform claim.
