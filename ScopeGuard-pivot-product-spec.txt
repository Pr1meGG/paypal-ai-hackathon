# 1. PRODUCT DECISION

**Decision: CONTINUE WITH PIVOT.**

This specification replaces the existing “mission-critical enterprise governance” positioning with a narrow product:

> **Evidence-backed paid amendments for small fixed-fee studios.**

This is a specification-only phase.

- No repository files were modified.
- No code was written.
- No commits, branches, PRs, or external payment operations were performed.
- The authoritative audit was read completely.
- Audit facts remain labeled:
  - **[A] VERIFIED**
  - **[B] REASONABLE INFERENCE**
  - **[C] UNVERIFIED / SPECULATIVE**

## Product name options

1. **ScopeGuard Amendments** — recommended for continuity.
2. **ScopeProof** — clearest expression of evidence grounding.
3. **ChangeReceipt** — emphasizes the link between scope and payment.
4. **AmendFlow** — neutral workflow-oriented name.

Product naming availability and trademark status are **[C] UNKNOWN — NOT VERIFIED**.

## Recommended name

**ScopeGuard Amendments**

The existing ScopeGuard name can survive if all unsupported enterprise, compliance, escrow, and autonomous-agent claims are removed.

## Product invariants

These are hard architectural rules:

1. AI can never create or mutate financial state.
2. AI can never set the final commercial price.
3. AI can never invent or silently accept evidence.
4. Every amendment item must reference the exact baseline version used for analysis.
5. A client must explicitly accept the exact merchant-approved amendment snapshot.
6. PayPal order amount and currency must come from the immutable merchant-approved snapshot.
7. `PAID` is legal only after independently verified PayPal capture evidence exists.
8. A failed, pending, malformed, mismatched, or unresolved payment can never become `PAID`.
9. PayPal request identities must be persisted and reused for retries.
10. Historical baselines, evidence, approvals, and payment receipts must remain reproducible.

# 2. PRODUCT THESIS

## One-sentence product definition

**ScopeGuard Amendments turns mixed client requests into evidence-backed amendment items, lets the studio approve the exact additional scope and price, collects the client’s PayPal payment, and marks the amendment paid only after verified PayPal evidence is bound to that amendment.**

## Product thesis

Fixed-fee studios do not primarily need another project dashboard. They need a trustworthy answer to a narrow question:

> “Which parts of this request are already included, which parts require a paid change, and can I prove what the client agreed to before I start?”

The product therefore focuses on one vertical slice:

```text
Client request
    ↓
Atomic request items
    ↓
Baseline evidence
    ↓
INCLUDED / EXTRA / UNCERTAIN
    ↓
Merchant-selected amendment
    ↓
Merchant-approved price
    ↓
Client acceptance
    ↓
PayPal Sandbox approval and capture
    ↓
Verified amendment receipt
```

The product does not claim to replace contract management, project management, invoicing, CRM, or legal review.

## User stories

### Studio owner

- As a studio owner, I can create a project and save the baseline SOW.
- As a studio owner, I can give a client a request link or enter a client request verbatim.
- As a studio owner, I can see each request decomposed into separate items.
- As a studio owner, I can inspect the exact SOW evidence behind every classification.
- As a studio owner, I can see when the system is uncertain.
- As a studio owner, I can select only grounded additional items for an amendment.
- As a studio owner, I can set the final price and currency.
- As a studio owner, I can approve the amendment without AI changing the amount.
- As a studio owner, I can see whether the client accepted the amendment.
- As a studio owner, I can see the verified PayPal capture tied to the exact amendment.

### Client

- As a client, I can review the proposed amendment without creating an account.
- As a client, I can see what was requested, what evidence supports it, and what I am being asked to pay.
- As a client, I can accept or decline the exact amendment snapshot.
- As a client, I can complete PayPal Sandbox approval.
- As a client, I can see whether payment is pending, failed, unresolved, or verified.

### System operator

- As an operator, I can distinguish AI analysis failure from payment failure.
- As an operator, I can reconcile an ambiguous PayPal response without marking it paid prematurely.
- As an operator, I can reproduce historical evidence against the exact baseline version used.

# 4. CORE USER JOURNEY

## Studio setup

1. Studio operator signs in using the MVP studio session.
2. Operator creates a project.
3. Operator enters:
   - Project name.
   - Client name.
   - Client email, optional.
   - Baseline SOW text.
4. Server creates immutable `BaselineVersion 1`.
5. Server calculates and stores the canonical text hash.
6. Studio receives a client request link.

## Client request

1. Client opens the request link.
2. Client submits the request in their own words.
3. Server stores the raw request without rewriting it.
4. The request is bound to the project’s current baseline version.

For the MVP, the product can also support a studio-side “paste client message” path. It must be labeled as a manually submitted client request, not represented as native Slack, Jira, or email ingestion.

## AI analysis

1. Server sends the request and the exact baseline version to the AI service.
2. AI decomposes the request into atomic items.
3. Each item is classified:
   - `INCLUDED`
   - `EXTRA`
   - `UNCERTAIN`
4. AI proposes evidence spans and explanations.
5. Server validates every evidence span.
6. Invalid evidence causes the item to become `UNCERTAIN`.
7. AI analysis never creates an amendment or changes payment state.

## Merchant review

1. Studio sees all request items.
2. Each item displays:
   - Original request text.
   - Normalized description.
   - Classification.
   - Exact evidence.
   - Explanation.
   - Uncertainty reason, if applicable.
3. Studio selects only grounded `EXTRA` items for the amendment.
4. `INCLUDED` items may be displayed in the amendment as no-charge context.
5. `UNCERTAIN` items cannot be included in a payable amendment.
6. Studio writes or edits the amendment wording.
7. Studio enters the final amount and currency.
8. Server creates an immutable merchant-approved amendment snapshot.

## Client acceptance

1. Client opens the amendment link.
2. Client sees:
   - Included context.
   - Additional work.
   - Evidence.
   - Amendment wording.
   - Final amount.
   - Currency.
3. Client explicitly accepts or declines.
4. Acceptance records the exact amendment snapshot hash.
5. The client cannot alter price, scope, evidence, or currency.

## PayPal payment

1. After client acceptance, the server creates a PayPal Sandbox order.
2. The order contains:
   - Exact approved amount.
   - Exact approved currency.
   - Amendment identifier as reconciliation metadata.
3. Client is redirected to PayPal Sandbox.
4. Client completes buyer approval.
5. Server verifies the order status and identity.
6. Server captures the order using the persisted capture operation key.
7. Server validates the actual capture response.
8. Only verified capture evidence can transition the amendment to `PAID`.

## Final receipt

The receipt displays the same amendment record with:

- Amendment ID.
- Baseline version ID and hash prefix.
- Selected amendment items.
- Evidence spans.
- Merchant approval timestamp.
- Client acceptance timestamp.
- Approved amount and currency.
- PayPal order ID.
- PayPal capture ID.
- Provider capture status.
- Verified amount and currency.
- Verification timestamp.
- Payment state.

# 6. STATE MACHINE

The system has three separate state machines.

## A. AI analysis state

```text
PENDING
   |
   v
ANALYZING
   |---------------------> FAILED
   |
   | all items grounded and classified
   v
ANALYZED

ANALYZING
   |
   | one or more items lack sufficient evidence
   v
NEEDS_CLARIFICATION
```

### AI transitions

| Transition | Trigger | Required evidence | Forbidden side effect |
|---|---|---|---|
| `PENDING → ANALYZING` | Server starts analysis | Valid request and baseline version | No amendment/payment mutation |
| `ANALYZING → ANALYZED` | Strict AI response and all evidence validate | Every item has valid classification; every non-uncertain item has valid evidence | No price or payment state |
| `ANALYZING → NEEDS_CLARIFICATION` | Item cannot be grounded or is ambiguous | Item-level uncertainty reason | Cannot create amendment from that item |
| `ANALYZING → FAILED` | Provider error, invalid JSON, schema violation | Error record | No partial analysis committed |
| `FAILED → ANALYZING` | Explicit retry | Same request and baseline version | No financial mutation |

`NEEDS_CLARIFICATION` does not prevent a merchant from creating an amendment from other fully grounded `EXTRA` items, but uncertain items cannot be selected or charged.

## B. Amendment state

```text
DRAFT
  |
  | merchant approves exact snapshot
  v
MERCHANT_APPROVED
  |
  | client accepts exact snapshot
  v
CLIENT_ACCEPTED
  |
  | payment operation begins
  v
PAYMENT_PENDING
  |
  | verified completed capture
  v
PAID
```

Terminal or non-happy-path states:

```text
DRAFT              → REJECTED
DRAFT              → STALE
MERCHANT_APPROVED  → CLIENT_DECLINED
MERCHANT_APPROVED  → EXPIRED
CLIENT_ACCEPTED    → CANCELLED
PAYMENT_PENDING    → PAYMENT_FAILED
PAYMENT_PENDING    → PAYMENT_UNRESOLVED
PAYMENT_FAILED     → PAYMENT_PENDING
PAYMENT_UNRESOLVED → PAYMENT_PENDING
```

### Amendment transition rules

#### `DRAFT → MERCHANT_APPROVED`

Triggered by:

- Authenticated studio session.

Required:

- At least one selected item.
- Every selected item is `EXTRA` or `INCLUDED`.
- No selected item is `UNCERTAIN`.
- Every selected item has valid evidence.
- Baseline version is not stale.
- Amount is a positive integer number of minor units.
- Currency is supported; MVP supports `USD`.
- Amendment wording exists.
- Snapshot hash is calculated and stored.
- `MERCHANT_APPROVED` event is appended.

Forbidden:

- AI-supplied amount.
- AI-supplied payment state.
- Mutation of the selected items after approval.

#### `MERCHANT_APPROVED → CLIENT_ACCEPTED`

Triggered by:

- Client using a valid amendment link.

Required:

- Amendment has not expired or been cancelled.
- Snapshot hash in the acceptance request matches the current amendment.
- Client acceptance timestamp is stored.
- `CLIENT_ACCEPTED` event is appended.

Forbidden:

- Client changing amount, currency, wording, or selected items.
- Order creation before acceptance is recorded.

#### `CLIENT_ACCEPTED → PAYMENT_PENDING`

Triggered by:

- Server starts PayPal order creation.

Required:

- Valid client acceptance.
- Immutable approved amount and currency.
- Stable order-creation operation key.
- Studio ownership of the amendment.

#### `PAYMENT_PENDING → PAID`

Triggered only by:

- Server-side PayPal verification.

Required:

- PayPal order ID matches the stored order.
- Capture ID exists.
- Capture status is `COMPLETED`.
- Captured amount exactly matches approved amount.
- Captured currency exactly matches approved currency.
- PayPal reference/custom ID matches amendment ID.
- Provider response is structurally valid.
- Verification transaction commits the payment evidence and amendment state together.

Forbidden:

- AI output.
- Client redirect alone.
- HTTP 200 alone.
- Missing capture ID.
- Local fallback.
- Pending, declined, failed, or unresolved response.
- A fabricated or locally generated PayPal identifier.

### Proof that failed payment cannot become paid

`PAID` has exactly one legal predecessor: a verified capture transaction.

No route accepts `classification`, `status`, or `capture_id` from the AI or browser as authority.

The database transition must require:

```text
current amendment state = PAYMENT_PENDING
AND payment attempt state = CAPTURED
AND verified capture evidence is complete
```

Otherwise the transition is rejected.

## C. Payment state

```text
NOT_STARTED
   |
   v
ORDER_CREATING
   |----------------------> FAILED
   |----------------------> UNRESOLVED
   |
   v
BUYER_APPROVAL_PENDING
   |
   | buyer return + verified order status
   v
BUYER_APPROVED
   |
   v
CAPTURE_IN_PROGRESS
   |-------------> CAPTURED
   |-------------> PENDING_FUNDS
   |-------------> FAILED
   |-------------> UNRESOLVED
```

Additional transitions:

- `PENDING_FUNDS → CAPTURED` after reconciliation proves completed capture.
- `PENDING_FUNDS → FAILED` after provider proves failure.
- `UNRESOLVED → CAPTURE_IN_PROGRESS` using the same operation key.
- `FAILED → ORDER_CREATING` only for a retryable order-creation failure.
- `FAILED → CAPTURE_IN_PROGRESS` if the existing order is still valid and buyer approval exists.
- `CAPTURED` is terminal for the payment attempt.
- No payment state can transition backward from `CAPTURED`.

# 7. AI CONTRACT

## AI input

The server sends:

- `change_request_id`
- Raw client request
- Exact `baseline_version_id`
- Canonical baseline text
- Deterministic line numbers
- Explicit instruction that the model has no financial authority

Example conceptual input:

```text
BASELINE VERSION: baseline_v1_hash
LINE 001: Three revision rounds are included.
LINE 002: HubSpot integration is excluded.
LINE 003: Mobile bug fixes are included.

CLIENT REQUEST:
Fix the mobile checkout bug and add HubSpot integration.
```

## AI output

Strict JSON only:

```json
{
  "schema_version": 1,
  "items": [
    {
      "request_text": "Fix the mobile checkout bug",
      "normalized_request": "Fix the mobile checkout bug",
      "classification": "INCLUDED",
      "evidence": {
        "start_line": 3,
        "end_line": 3,
        "quote": "Mobile bug fixes are included."
      },
      "reasoning_summary": "The request matches the stated mobile bug-fix inclusion.",
      "uncertainty_reason": null,
      "suggested_amendment_wording": null
    },
    {
      "request_text": "add HubSpot integration",
      "normalized_request": "Add HubSpot integration",
      "classification": "EXTRA",
      "evidence": {
        "start_line": 2,
        "end_line": 2,
        "quote": "HubSpot integration is excluded."
      },
      "reasoning_summary": "The request is explicitly excluded from the baseline.",
      "uncertainty_reason": null,
      "suggested_amendment_wording": "Add HubSpot integration as a paid amendment."
    }
  ]
}
```

## Allowed fields

The model may return:

- Request text.
- Normalized request.
- Classification.
- Evidence span.
- Reasoning summary.
- Uncertainty reason.
- Suggested amendment wording.

The model may not return:

- Amount.
- Currency.
- Payment status.
- PayPal order ID.
- PayPal capture ID.
- Merchant approval.
- Client acceptance.
- `PAID`.
- “Completed.”
- Receipt data.
- Objective probability or calibrated confidence.

## Classification rules

### `INCLUDED`

Use only when:

- The request is supported by specific baseline evidence.
- The evidence is validated by the server.
- The request is within the stated baseline terms.

### `EXTRA`

Use only when:

- The request is explicitly excluded, or
- The request clearly adds a deliverable not contained in the baseline.
- The evidence supports the boundary.
- The server validates the evidence.

### `UNCERTAIN`

Use when:

- The baseline is silent.
- The language is ambiguous.
- The request conflicts with multiple clauses.
- The item cannot be decomposed reliably.
- Evidence is missing or fails validation.
- The model is asked to infer a legal or commercial conclusion unsupported by the text.

`UNCERTAIN` is a valid product result, not an error to be hidden.

## Server validation

The AI response is parsed through a strict schema:

- Unknown fields rejected.
- Unsupported classifications rejected.
- Missing required fields rejected.
- Request text must appear in the raw client request.
- Evidence line ranges must be within the referenced baseline version.
- Evidence quote must exactly match the canonical baseline text for that span.
- The baseline hash must match the hash supplied to the AI request.
- Invalid evidence converts the item to `UNCERTAIN` or fails the analysis.
- Any model output containing `PAID` is rejected and cannot mutate payment state.

No silent heuristic fallback is allowed in the product path. If the model is unavailable:

- Analysis becomes `FAILED`.
- The UI explains that analysis could not be completed.
- A test-only fake AI adapter may be used in automated tests.
- A deterministic keyword analyzer must never be presented as semantic AI.

# 8. EVIDENCE-GROUNDING DESIGN

## Chosen implementation

Use deterministic line-based evidence validation. Do not add a vector database.

### Baseline ingestion

When a baseline is saved:

1. Preserve the submitted source text.
2. Normalize line endings to `LF`.
3. Generate canonical line numbers.
4. Calculate SHA-256 over canonical text.
5. Store the immutable `BaselineVersion`.

### AI citation format

The AI returns:

- `start_line`
- `end_line`
- `quote`

The server checks:

1. The referenced baseline version belongs to the same project.
2. The line range exists.
3. The concatenated baseline lines exactly match the quote.
4. The baseline hash matches the hash supplied to the AI request.
5. The evidence span is stored against that exact version.
6. The evidence is not reused from another project or version.

### Why no vector database

For the hackathon MVP:

- SOWs are expected to be short enough for a line-numbered prompt.
- Exact evidence validation is more important than semantic retrieval sophistication.
- A vector database would add:
  - Infrastructure.
  - Embedding version management.
  - Retrieval reproducibility problems.
  - Additional failure modes.
- The product’s differentiator is verifiable evidence, not retrieval infrastructure.

If a baseline exceeds the supported context limit, the system should reject it with a clear message rather than silently truncating it.

## Evidence invariants

- No evidence reference without a baseline version.
- No evidence quote without exact source matching.
- No amendment item without valid evidence.
- No historical evidence rewritten after a new baseline upload.
- No section number accepted as proof by itself.
- No evidence copied from another project or baseline.

# 9. COMMERCIAL AUTHORITY

## Pricing model

The merchant owns final pricing.

MVP pricing flow:

```text
AI identifies request items
        ↓
Merchant selects grounded EXTRA items
        ↓
Merchant writes or edits amendment wording
        ↓
Merchant enters amount_minor and currency
        ↓
Server validates amount/currency
        ↓
Merchant approves immutable snapshot
```

## Pricing rules

- No AI-generated price.
- No keyword multiplication.
- No “fair market” estimate.
- No automatic rate calculation.
- No amount supplied by the client.
- No amount inferred from the SOW.
- No currency conversion in the MVP.
- MVP currency: `USD`.
- Amount is stored as integer minor units.
- Amount must be greater than zero for a paid amendment.
- An included-only request does not create a payable amendment.

A future rate-card feature may be added after customer validation. It is not part of this MVP.

## Merchant approval record

Merchant approval stores:

- Studio ID.
- Merchant session subject.
- Amendment ID.
- Selected amendment item IDs.
- Exact scope wording.
- Amount.
- Currency.
- Baseline version ID.
- Baseline hash.
- Amendment snapshot hash.
- Approval timestamp.

Once approved:

- Scope cannot be edited.
- Selected items cannot change.
- Amount cannot change.
- Currency cannot change.
- A correction requires cancelling the draft/approved amendment and creating a new amendment revision.

## Client acceptance

Client acceptance records:

- Amendment ID.
- Snapshot hash.
- Acceptance timestamp.
- Client link identity.
- Optional client display name.

Client acceptance does not permit any financial mutation other than advancing the accepted amendment into payment initiation.

# 10. PAYPAL PAYMENT ARCHITECTURE

## Official flow

```text
OAuth client credentials
        ↓
Create PayPal Orders v2 order
        ↓
Persist order ID and approval URL
        ↓
Buyer approval at PayPal Sandbox
        ↓
Verify order identity and APPROVED state
        ↓
Capture order using stable request ID
        ↓
Verify capture response
        ↓
Persist verified evidence
        ↓
Mark amendment PAID
```

PayPal remains central because it performs the actual client payment and produces the receipt evidence. The application does not simulate a successful payment.

## MVP API surfaces

### Studio-protected

```text
POST /api/projects
POST /api/projects/{project_id}/baseline-versions
GET  /api/projects/{project_id}
GET  /api/projects/{project_id}/amendments

POST /api/change-requests/{request_id}/analyze
POST /api/change-requests/{request_id}/amendments
POST /api/amendments/{amendment_id}/merchant-approve
POST /api/amendments/{amendment_id}/reconcile
GET  /api/amendments/{amendment_id}
```

### Client-link protected

```text
GET  /client/projects/{client_token}
POST /client/projects/{client_token}/requests

GET  /client/amendments/{amendment_token}
POST /client/amendments/{amendment_token}/accept
```

### PayPal callback

```text
GET /api/paypal/return
GET /api/paypal/cancel
```

The callback does not trust the browser’s `token` alone. It must match a stored PayPal order belonging to the expected amendment.

## Order creation

The server creates the order only after:

- Merchant approval exists.
- Client acceptance exists.
- Amendment snapshot is immutable.
- Amount and currency are validated.
- A stable order operation key is persisted.

The PayPal order should include:

- `intent: CAPTURE`
- Approved amount.
- Approved currency.
- Amendment ID in supported reconciliation metadata such as `reference_id` or `custom_id`.
- Configured public return URL.
- Configured public cancel URL.

The application must not create synthetic order IDs or approval URLs.

## Buyer approval

After return from PayPal:

1. Extract the provider order token.
2. Compare it to the stored PayPal order ID.
3. Fetch order details from PayPal.
4. Require the order to be in an approval-compatible state.
5. Record buyer approval as a payment-state transition.
6. Begin capture.

The return page itself never means payment succeeded.

## Capture verification

The server should request a complete representation where supported, or retrieve details after a minimal response.

The response is accepted as payment evidence only if:

- HTTP response is successful.
- Order ID matches.
- Capture ID exists.
- Capture status is `COMPLETED`.
- Capture amount equals amendment amount exactly.
- Capture currency equals amendment currency exactly.
- Provider reference/custom ID matches the amendment.
- The capture is associated with the expected PayPal order.
- The response contains sufficient provider evidence to reproduce the decision.

The server then commits:

1. Payment evidence.
2. Payment state `CAPTURED`.
3. Amendment state `PAID`.
4. `PAYMENT_CAPTURE_VERIFIED` event.

These must occur in one local transaction.

## Persisted PayPal evidence

Persist at minimum:

- PayPal order ID.
- PayPal capture ID.
- Order status.
- Capture status.
- Requested amount.
- Requested currency.
- Verified captured amount.
- Verified captured currency.
- Provider reference/custom ID.
- PayPal fee if returned.
- Provider create/update timestamps.
- Approval URL.
- Operation key.
- Sanitized provider response.
- Local verification timestamp.
- Amendment ID.

Do not persist:

- Client secret.
- OAuth access token.
- Full sensitive payment credentials.
- Unnecessary payer information.

## Webhooks

Webhooks are **not required for the MVP**.

Reason:

- Synchronous capture plus immediate provider verification is enough for the hackathon’s single-payment flow.
- A fake browser webhook interface would create false confidence.
- Genuine webhook support requires:
  - Public HTTPS endpoint.
  - Signature verification.
  - Duplicate event handling.
  - Event persistence.
  - Reconciliation policy.

The data model should remain extensible to webhooks through `PaymentAttempt` and `AmendmentEvent`.

A future webhook implementation may update unresolved payment attempts, but it must use the same verification and amount-binding rules.

# 11. PAYMENT FAILURE + RETRY MODEL

## Failure states

| Scenario | Payment state | Amendment state | Allowed action |
|---|---|---|---|
| Order creation rejected | `FAILED` | Remains `CLIENT_ACCEPTED` | Retry if parameters unchanged |
| Network timeout creating order | `UNRESOLVED` | Remains `CLIENT_ACCEPTED` | Retry same operation key or reconcile |
| Buyer abandons checkout | `BUYER_APPROVAL_PENDING` | `PAYMENT_PENDING` | Resume or cancel |
| Buyer cancels checkout | `FAILED` or `NOT_STARTED` | `CLIENT_ACCEPTED` | Resume or cancel |
| Capture declined | `FAILED` | `PAYMENT_FAILED` | Retry if PayPal permits |
| Capture returns pending funds | `PENDING_FUNDS` | `PAYMENT_UNRESOLVED` | Reconcile later |
| Capture returns HTTP 5xx | `UNRESOLVED` | `PAYMENT_UNRESOLVED` | Retry same capture key |
| Capture response malformed | `UNRESOLVED` | `PAYMENT_UNRESOLVED` | Reconcile; never mark paid |
| Unknown order | No mutation | No mutation | Return 404/error |
| Already captured | Reconcile | `PAID` only after matching capture evidence | No second capture |
| Amount mismatch | `FAILED` or `UNRESOLVED` | Never `PAID` | Manual reconciliation |
| Currency mismatch | `FAILED` or `UNRESOLVED` | Never `PAID` | Manual reconciliation |
| Missing capture ID | `UNRESOLVED` | Never `PAID` | Reconcile provider state |
| Verified completed capture | `CAPTURED` | `PAID` | Receipt available |

## Ambiguous provider response

An ambiguous response means:

- The provider may have processed the operation.
- The application cannot yet prove the final state.
- The provider response is missing required evidence.
- A timeout occurred after the request was sent.
- A 5xx response leaves the remote result unknown.

The application must:

1. Store `UNRESOLVED`.
2. Preserve the operation key.
3. Preserve any known order/capture IDs.
4. Avoid generating replacement IDs.
5. Avoid creating a new order blindly.
6. Offer a reconcile action.
7. Query PayPal using the known order ID.
8. Mark `PAID` only if matching completed capture evidence is found.
9. Otherwise keep the amendment unresolved.

## Already-captured order

If capture returns a conflict or already-captured response:

1. Do not issue a second capture.
2. Fetch PayPal order details.
3. Inspect the capture list.
4. Find the capture associated with the expected order and amendment.
5. Validate amount, currency, status, and reference.
6. Mark `PAID` only if all checks pass.
7. Otherwise remain unresolved.

## No local fallback

The following are prohibited:

- `ORDER-MOCK-*`
- `CAP-*` locally generated as receipts.
- Sandbox-looking URLs generated without PayPal response.
- Returning HTTP 200 success after provider failure.
- Returning `COMPLETED` from a local default.
- Inventing payer email or fees.
- Treating a redirect as payment proof.

## Idempotency strategy

### Order creation

- Generate one UUID for the logical order-creation operation.
- Persist it before the provider request.
- Use it as `PayPal-Request-Id`.
- Reuse it after timeout or 5xx.
- Do not generate another key unless creating a genuinely new amendment snapshot.

### Capture

- Generate one UUID for the logical capture operation.
- Persist it before the first capture request.
- Reuse it for every retry of that capture.
- Associate it with `(amendment_id, paypal_order_id)`.
- Do not use a new request ID merely because the first response was unclear.

### Database constraints

- Unique operation key.
- Unique logical capture operation per PayPal order.
- One active open amendment per project for MVP.
- One approved snapshot per amendment.
- One verified capture per amendment.

### Changed commercial terms

If amount, currency, or selected scope changes:

1. Cancel the old amendment or leave it as a historical rejected revision.
2. Create a new amendment.
3. Generate new operation keys.
4. Never reuse old PayPal order or capture identity.

# 12. AUTHORIZATION MODEL

## MVP authority model

No enterprise authentication is needed, but financial operations require ownership semantics.

### Studio session

Use a minimal demo session:

- Studio operator authenticates through `/api/demo/login`.
- Server validates a configured `DEMO_STUDIO_KEY`.
- Server issues an HttpOnly, Secure-in-deployment, SameSite cookie.
- Cookie maps to one configured `studio_id`.
- All merchant routes require this session.
- Every project, amendment, and reconciliation query is filtered by `studio_id`.

The key is a demo credential, not a production account. It must not be committed to the repository.

### Client access

Clients do not need accounts.

Use a signed, scoped client token containing:

- Resource ID.
- Role.
- Purpose.
- Expiration.
- Nonce.

Examples:

- Project request token.
- Amendment review/acceptance token.

The server must verify:

- Signature.
- Purpose.
- Expiry.
- Resource ownership.
- Current state.

Client tokens cannot access:

- Other projects.
- Merchant routes.
- Provider credentials.
- Internal error details.
- Unapproved draft amendments.

### PayPal callback authority

The PayPal return URL is public but restricted by:

- Known stored PayPal order ID.
- Expected amendment ID.
- Provider order lookup.
- Exact order ownership.
- Exact amount/currency/reference matching.

A callback token cannot create or approve an amendment by itself.

## Explicitly out of scope

- User registration.
- Password reset.
- Enterprise identity providers.
- Multi-user roles.
- Tenant administration.
- Team invitations.
- Production-grade session revocation.
- SSO.

- The amendment.

- The provider reference.

A failed or ambiguous PayPal response remains failed or unresolved. It does not become a polished fake receipt.

These are not proven market-exclusive capabilities. They are the technical/product behaviors the hackathon build can credibly demonstrate.

# 18. TEST STRATEGY

Tests must prove invariants, not merely return HTTP 200.

## A. Evidence grounding

- Valid evidence span is accepted.
- Quote with one changed word is rejected.
- Line range outside the baseline is rejected.
- Evidence from another project is rejected.
- Evidence from an older baseline version is rejected against the current version.
- Evidence with duplicate ambiguous matches becomes `UNCERTAIN`.

## B. Included/excluded counterfactuals

Use the same request against two baselines:

```text
Baseline A: HubSpot integration is included.
Baseline B: HubSpot integration is excluded.
```

Expected:

- Baseline A: `INCLUDED`.
- Baseline B: `EXTRA`.
- Same request must not produce the same hardcoded result.

## C. Mixed requests

Given:

```text
Fix the mobile checkout bug and add HubSpot integration.
```

Expected:

- Two request items.
- Mobile bug: `INCLUDED`.
- HubSpot: `EXTRA`.
- Separate evidence spans.
- One amendment can select only HubSpot.

## D. Uncertainty / abstention

- Silent baseline clause produces `UNCERTAIN`.
- Conflicting clauses produce `UNCERTAIN`.
- Uncertain item cannot be selected for a paid amendment.
- Analysis remains `NEEDS_CLARIFICATION`.

## E. Evidence fabrication rejection

AI output claiming:

```text
Section 7.1 says HubSpot is excluded.
```

when no such section exists must:

- Fail evidence validation.
- Produce `UNCERTAIN` or analysis failure.
- Create no payable amendment from that item.

## F. Amendment state transitions

Test:

- Legal draft creation.
- Legal merchant approval.
- Legal client acceptance.
- Illegal direct `DRAFT → PAID`.
- Illegal `AI → PAID`.
- Illegal approval with uncertain item.
- Illegal approval with stale baseline.
- Illegal edit after merchant approval.
- Cancellation behavior.
- Expiration behavior.

## G. Merchant approval

Test:

- Missing merchant session returns unauthorized.
- Wrong studio cannot access the project.
- Negative amount rejected.
- Zero amount rejected for paid amendment.
- Unsupported currency rejected.
- Merchant snapshot hash is persisted.
- Amount cannot be changed after approval.

## H. Client acceptance

Test:

- Invalid token rejected.
- Expired token rejected.
- Token for another amendment rejected.
- Acceptance records exact snapshot hash.
- Client cannot change price or scope.
- Repeated acceptance is idempotent and does not create duplicate payment operations.

## I. PayPal order creation failure

Test with a provider fake:

- Timeout.
- HTTP 400.
- HTTP 401.
- HTTP 500.
- Malformed response.
- No order ID.
- No approval URL.

Expected:

- No synthetic order ID.
- No synthetic URL.
- No `PAID`.
- Correct failed or unresolved state.

## J. Capture failure

Test:

- Declined capture.
- HTTP 422.
- HTTP 500.
- Provider exception.
- Capture response missing nested payment data.

Expected:

- No `PAID`.
- No fake capture ID.
- Payment evidence records the failure.

## K. Pending capture

Test:

- Provider capture status `PENDING`.
- Seller receivable breakdown absent.

Expected:

- Payment remains pending/unresolved.
- Amendment remains unpaid.
- Reconciliation remains available.

## L. Amount mismatch

Provider returns completed capture for the wrong amount.

Expected:

- No `PAID`.
- Payment becomes unresolved.
- Mismatch is recorded.
- Manual reconciliation required.

## M. Currency mismatch

Provider returns completed capture in the wrong currency.

Expected:

- No `PAID`.
- No local currency substitution.
- Mismatch is recorded.

## N. Unknown order

Attempt capture or reconciliation for an unknown PayPal order.

Expected:

- Error response.
- No local amendment mutation.
- No receipt.

## O. Retry/idempotency

Test:

- Same create request repeated after timeout.
- Same capture request repeated after timeout.
- Same operation key reused.
- No second logical order.
- No second logical capture.
- Stored provider response returned when available.

## P. Provider timeout

Test provider success followed by local timeout.

Expected:

- Local state becomes `UNRESOLVED`.
- Operation key and order ID remain available.
- Reconciliation can discover the completed payment.
- Only matching provider evidence transitions to `PAID`.

## Q. Model output containing `PAID`

Inject AI output containing:

```json
{
  "classification": "PAID"
}
```

Expected:

- Strict schema rejects it.
- Analysis fails or becomes unresolved.
- No amendment is paid.
- No payment attempt is created.
- No financial record is mutated.

This is the most important AI/financial isolation test.

Test:

- Anonymous merchant approval.
- Anonymous order creation.
- Wrong studio access.
- Client token attempting merchant action.
- Client token attempting reconciliation.

Expected:

- Authorization failure.
- No state mutation.

2. Analyze request against v1.
3. Create amendment referencing v1.
4. Create baseline v2.
5. Read v1 evidence and amendment.

# 20. DEFINITION OF DONE

The MVP is done only when all required criteria pass.

## Product behavior

- A real SOW can be stored.
- A new immutable baseline version can be created.
- A real client request can be submitted.
- The request is bound to the exact baseline version.
- AI decomposes the request into atomic items.
- Each item is `INCLUDED`, `EXTRA`, or `UNCERTAIN`.
- AI can abstain.
- Evidence is validated against the exact baseline text.
- Fabricated evidence is rejected.
- Merchant selects the final amendment scope.
- Merchant controls the final amount.
- Merchant controls the final currency.
- Merchant approves an immutable amendment snapshot.
- Client explicitly accepts the exact snapshot.
- Client cannot alter the amount or scope.
- A PayPal Sandbox order is genuinely created.
- Buyer approval genuinely occurs.
- Capture genuinely occurs.
- Capture is independently verified.
- PayPal order and capture are bound to the exact amendment.
- Amount matches.
- Currency matches.
- Provider reference matches.
- Verified PayPal evidence is persisted.
- Only then does the amendment become `PAID`.
- Historical evidence remains reproducible.

- Failed order creation cannot become success.
- Buyer abandonment cannot become paid.
- Declined capture cannot become paid.
- Pending capture cannot become paid.
- Malformed provider response cannot become paid.
- Missing capture ID cannot become paid.

- Currency mismatch cannot become paid.

- AI output containing `PAID` cannot create financial state.

# 21. OPEN QUESTIONS

These are unresolved product or delivery questions. They are not silently treated as facts.

## Customer validation

1. Will fixed-fee studios accept a separate amendment tool rather than using an existing invoicing/proposal system?
2. Do target studios prefer payment before work begins, or payment after a signed amendment?
3. Which studio segment should be tested first: web development, design, branding, or marketing?

**Default for hackathon:** small web/design studios.

## Client submission

4. Is a public client request link required for the submission, or is studio-side paste of a verbatim client message sufficient?
5. Should clients be able to submit multiple requests against the same baseline?

**Default:** support one project-scoped request link and allow multiple requests, with one open amendment at a time.

## Payment

6. Is USD sufficient for the target demo?
7. Is synchronous capture acceptable for the first product version?
8. Is a manually operated reconciliation action acceptable instead of webhooks?

**Default:** USD only, CAPTURE flow, no webhooks, owner-triggered reconciliation.

## Baseline lifecycle

9. Should an explicitly paid amendment be manually applied into a new baseline?
10. What should happen when the studio uploads a new SOW while an amendment is open?

**Default:** paid amendments do not silently rewrite the baseline. Draft amendments become stale when the baseline changes; approved or accepted open amendments block replacement until cancelled or completed.

## Authentication and deployment

11. Will the final demo run locally, on a hosted preview, or both?
12. How will judges receive a safe demo access code?
13. Is the public PayPal return URL available for the chosen environment?

**Default:** one configured demo studio session, client access through signed links, and a documented Sandbox setup.

16. Should provider response bodies be retained in full or only as sanitized evidence?

**Default:** retain only sanitized provider fields needed for reconciliation; avoid unnecessary payer data.

17. Does the studio need to charge for included and extra items in one amendment?

**Default:** uncertain items cannot be selected, but grounded extra items may proceed with an explicit warning.

## FINAL CALL

**CONTINUE WITH PIVOT**

- The surviving problem is credible enough for a focused hackathon product.
- The existing repository contains reusable FastAPI, persistence, PayPal, and visual foundations.
- The current product must be narrowed from enterprise governance to paid amendments.
- AI has a meaningful role in decomposition, evidence discovery, and abstention.
- AI must not control price, approval, or payment state.
- Exact evidence validation is feasible without a vector database.
- PayPal can be central through a genuine Sandbox order, approval, capture, and verification flow.
- The strongest demonstrable differentiators are evidence grounding, version binding, and amendment-to-capture binding.
- The existing frontend, payment fallback behavior, tests, and documentation require substantial rewrite.
- The pivot should be rejected if real customer validation or a genuine PayPal Sandbox flow cannot be demonstrated before submission.
